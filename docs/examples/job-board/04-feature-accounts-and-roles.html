04 — First feature: accounts and roles via write-spec → approval → ship-feature (HIRE-3)

Date in the story: 2026-10-21 · Route: feature → write-spec → approval → ship-feature Ticket: HIRE-3 · Session: started in the workspace root ~/work/hireboard Spec: artifacts/api/.ai/specs/spec-HIRE-3-accounts-and-roles/

Chapter 03 ended with ADR-0001 accepted: the API issues Sanctum personal access tokens, and the Next.js server keeps them in the HttpOnly hireboard_session cookie. Now HIRE-3 turns that decision into code. Candidates and employers can register, sign in, see a dashboard and sign out. Employers get a company when they register. Guests can still browse jobs.

HIRE-3 is the first ticket that takes the full feature pipeline, and the pipeline's order is fixed:

/sdd HIRE-3 → feature (confirmed) → write-spec → human approval → ship-feature { spec } → PRs

You will run each step once. The commands and arguments shown are the real ones. Agent output is abridged and marked simulated, because your run will word things differently.

In plugin mode the entry point is namespaced: type /sdd-kit:sdd wherever this chapter shows /sdd (see INSTALLATION.md).

Before you start

  • ADR-0001 is Accepted in api/docs/adr/0001-spa-auth.md, and INV-05 and BR-04 are in context (chapter 03).
  • Both dev servers are running, because the Visual phase drives a real browser:
    cd ~/work/hireboard/api && php artisan migrate:fresh --seed && php artisan serve --port=8000
cd ~/work/hireboard/web && npm run dev            # second terminal
  • The Claude in Chrome extension is connected if you want the Visual phase to run. Without it, Visual logs "could not run" and the rest of the pipeline continues.

Create the feature branch in each repo now, so that every file the pipeline writes lands on it:

Acceptance criteria (EARS, one observable outcome each; shortened here):

IDCriterion
AC-1WHEN a visitor registers as candidate THE SYSTEM SHALL respond 201 with {user, token}
AC-2WHEN a visitor registers as employer with company_name THE SYSTEM SHALL also create one company owned by them, slug suffixed -2, -3 … while taken (BR-02)
AC-3IF the role is admin THEN THE SYSTEM SHALL respond 422 and create nothing (BR-01)
AC-4IF the email exists, compared case-insensitively, THEN THE SYSTEM SHALL respond 422 (BR-03)
AC-5WHEN credentials are valid THE SYSTEM SHALL respond 200 with a web token that expires in 7 days (BR-04)
AC-6IF the email is unknown or the password wrong THEN THE SYSTEM SHALL respond 422 invalid_credentials
AC-7WHEN a user logs out THE SYSTEM SHALL revoke that token only, respond 204, and /me with it SHALL return 401
AC-8WHEN a signed-in user requests /me THE SYSTEM SHALL return exactly {id, name, email, role}
AC-9IF more than 6 register/login requests (one shared bucket per client) arrive within a minute THEN THE SYSTEM SHALL respond 429
AC-10WHEN a user signs in on /login THE web app SHALL set the HttpOnly hireboard_session cookie and redirect to /dashboard; JS can't read the token (manual)
AC-11WHEN a guest opens /dashboard THE web app SHALL redirect to /login?next=/dashboard (manual)

Why spec is a path here (kit friction F2). The SKILL.md example passes a bare folder name, which works when the session starts inside the repo that holds the spec. ship-feature's Spec phase resolves the reference under .ai/specs/ relative to the session's directory, and in the workspace root that directory holds no specs. Step 7 — Reading the code the pipeline wrote

You should still read what the pipeline produced before you open a PR. These excerpts show how the kit's conventions shaped the auth code. The full files are the artifacts linked below.

AuthService never touches Eloquent. Token issuing and revoking sit behind UserRepositoryInterface, so the service works only with DTOs (AuthService.php, UserRepositoryInterface.php):

public function register(RegisterUserDTO $data): AuthResultDTO
{
    return DB::transaction(function () use ($data): AuthResultDTO {
        $user = $this->users->create($data);

        if ($data->isEmployer() && $data->companyName !== null) {
            $this->companies->createForOwner($user->id, $data->companyName);
        }

        return new AuthResultDTO($user, $this->users->issueToken($user->id));
    });
}

The 7-day lifetime (BR-04) is set where the token is created, so config/sanctum.php stays untouched (UserRepository.php):

return $user->createToken(self::TOKEN_NAME, ['*'], now()->addDays(self::TOKEN_LIFETIME_DAYS))->plainTextToken;

Logout revokes whatever token the request carried (PersonalAccessToken::findToken($bearer)?->delete()). That has the same effect as the ADR's currentAccessToken()->delete(), without passing a model into the service. Other devices stay signed in (AC-7).

RegisterUserDTO carries BR-01 and BR-03 in its rules. Emails are lowercased in prepareForPipeline(), which laravel-data runs before validation. So unique:users,email sees casey@hireboard.test even when the visitor typed Casey@Hireboard.TEST (AC-4). (RegisterUserDTO.php):

'role' => ['required', 'string', Rule::in(UserRole::selfRegistrable())],
'company_name' => ['nullable', 'required_if:role,employer', 'string', 'min:2', 'max:120'],

Slug suffixing lives in CompanyRepository::createForOwner (BR-02). Acme Robotics becomes acme-robotics, then acme-robotics-2 while that slug is taken, and the unique index on companies.slug is the final guard. CompanyRepository.php is a shared file that later chapters extend, so its artifact is kept with chapter 02 (CompanyRepository.php). HIRE-3 added this method:

public function createForOwner(int $ownerId, string $name): CompanyDTO

lib/session.ts owns the cookie. The flags implement INV-05 and ADR-0001 (session.ts):

store.set(SESSION_COOKIE, token, {
  httpOnly: true,
  sameSite: 'lax',
  secure: process.env.NODE_ENV === 'production',
  path: '/',
  maxAge: SESSION_MAX_AGE_SECONDS, // 7 days, same as the token
});

getCurrentUser() is wrapped in React's cache(), so a layout and its page share one /me call per request. It returns null on a 401, which happens when a cookie outlives its revoked or expired token.

loginAction is a Server Action. It maps API error codes to messages and keeps redirect() outside the try, because redirect() works by throwing (actions.ts):

try {

} catch (error) {
  return toFormState(error, 'Sign-in failed. Please try again.');
}

redirect(safeNext(formData.get('next')));

Commit in each repo separately. The spec folder is committed with api/, because that's where it lives:

Merge api first. The change is additive: new routes, a new column with a default, and no change to existing response shapes (MNC-1). A deployed API with HIRE-3 still serves the old web build.
