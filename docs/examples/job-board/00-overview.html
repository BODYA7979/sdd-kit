00 — Hireboard from scratch: overview and prerequisites

This walkthrough builds a small job board called Hireboard from an empty folder to a team-ready product. It uses SDD Kit v2.0.0 for every step. Each chapter is one real ticket, taken through the /sdd route the kit picks for it. Read the chapters in order to follow the story, or jump to the one that matches the route you are about to use.

Hireboard, the people involved, and every session transcript are fictional. Agent output in the chapters is simulated: it is abridged and marked as such. The code and documents under artifacts/ are complete files you can drop onto fresh scaffolds.

The product

Visitors search open job postings by keyword, location, remote and employment type, and open a company's careers page. Candidates register, keep a private profile, apply to open jobs, and review companies (one review per company). An admin moderates every review before it goes public. Employers register together with their company and see the applications to their jobs.

The product owner is Maya Chen. She approves specs and the ADR. The developer is Alex Rivera, who runs the Claude Code sessions. Ticket keys use the HIRE prefix. No tracker is connected, so ticket text is pasted into /sdd. The timeline runs from 2026-10-19 to 2026-11-03.

The shape of the system

Two git repos sit side by side in a parent-folder workspace that has no git of its own. This is the layout from docs/multi-repo.md, with real repo names in place of be/ and fe/.

~/work/hireboard/              no .git; start Claude here for cross-repo work
├── CLAUDE.md                  workspace contract: @api/CLAUDE.md, @web/CLAUDE.md, routing, process
├── product-brief.md           input to greenfield-build
├── .ai/                       local scratch (anything written while a session runs here)
├── api/                       Laravel 12 JSON API     git@github.com:hireboard/api.git
└── web/                       Next.js 15 App Router   git@github.com:hireboard/web.git

At runtime the browser only talks to Next.js. The Next.js server holds the Sanctum token in an HttpOnly cookie and calls the API with it (the "backend for frontend" pattern, decided in chapter 03 as ADR-0001):

 Browser                      Next.js server (web/)                 Laravel API (api/)
 localhost:3000               localhost:3000                        localhost:8000
┌──────────────┐  request +  ┌────────────────────────────┐ Bearer ┌──────────────────────┐
│ pages, forms │ ──────────▶ │ Server Components,         │ ─────▶ │ /api/v1/*            │
│ no token in  │   cookie    │ Server Actions             │ token  │ Sanctum PATs ('web', │
│ JavaScript   │ ◀────────── │ lib/api/client.ts reads    │ ◀───── │ 7-day expiry)        │
└──────────────┘    HTML     │ cookie hireboard_session   │  JSON  │ SQLite               │
                             └────────────────────────────┘        └──────────────────────┘
  • The API serves /api/v1 with a { success, status, message, data } envelope. It uses invokable controllers, services, DTOs (Spatie Laravel Data) and repositories behind interfaces.
  • Next.js reads API_BASE_URL=http://localhost:8000 from web/.env.local. That variable is server-only, never NEXT_PUBLIC_. The browser never calls :8000, so no CORS config is needed.
  • http://localhost:3000 is the url argument passed to every workflow for browser acceptance.

Route map

/sdd is the single front door (src/skills/sdd/SKILL.md). It sorts each request into one of six routes, confirms the route with you, collects the inputs, and launches exactly one fixed pipeline:

/sdd <ticket-id | description>
   ├─ trivial   → /simple-task                  (no spec)
   ├─ bug       → fix-bug workflow
   ├─ decision  → tech-research workflow → ADR
   ├─ feature   → /write-spec → HUMAN APPROVAL → ship-feature { spec }
   ├─ shipped   → qa-and-docs workflow
   └─ new app   → greenfield-build workflow

Plugin or file-copy?

INSTALLATION.md#choose-a-mode compares the two modes. For this walkthrough the choice comes down to one constraint: api/ and web/ must not exist before chapter 02. composer create-project and create-next-app need a missing or empty target folder, and greenfield-build's Detect phase stops when it finds tracked files. Chapter 01 shows both safe options:

  • Plugin mode (recommended here). Install once with /plugin marketplace add stasmarkov/sdd-kit and /plugin install sdd-kit@sdd-kit (chapter 01, step 2), and nothing is written into the repos. Plugins do not create CLAUDE.md, AGENTS.md or .claude/rules/, so chapter 02 copies them by hand (INSTALLATION.md#project-context-is-not-installed).
  • File-copy mode. Run ./install.sh --project inside each repo after greenfield-build has scaffolded it, never before.

How to read the artifacts

Every file the walkthrough produces is under artifacts/, mapped like this:

In this folderIn your workspace
artifacts/workspace/**~/work/hireboard/**
artifacts/api/**~/work/hireboard/api/** (a fresh Laravel 12 app after the scaffold commands)
artifacts/web/**~/work/hireboard/web/** (a fresh create-next-app@15 app after the scaffold commands)
artifacts/kit-fork/**a fork of the SDD Kit repo (the team eval case in chapter 11)
  • Each file belongs to the chapter that first creates it and shows its end-of-walkthrough state.
  • A later change to that file appears in the later chapter as a diff, for example the HIRE-8 salary formatting in web/components/job-card.tsx, or the HIRE-9 fix in the API's JobPostingRepository.
  • Some files grow with every feature: web/lib/api/endpoints.ts, api/docs/api/api-contracts.md, api/docs/context/business-rules.md, api/bootstrap/app.php and RepositoryServiceProvider. They also show their final state, so reading one mid-story shows entries from later chapters.
  • composer.json and package.json are not artifacts. Dependencies come from the scaffold commands in chapter 02.

Cost and effort

Workflows (greenfield-build, tech-research, ship-feature, fix-bug, qa-and-docs) fan out many agents in the background, so they cost far more tokens than a single chat. Phases name a tier rather than a model:

  • deep for investigation, specs, review and decisions
  • standard for implementation and fixes
  • light for inventory

docs/effort-guidelines.md maps the tiers to models. It also shows how a team pins exact model IDs, either in MODEL_TIERS or per run with the models argument:

Workflow({ name: "ship-feature", args: { spec: "...", models: { standard: { model: "<pinned id>", effort: "high" } } } })

This walkthrough leaves the defaults alone and quotes no prices. Check current pricing yourself.

No workflow starts on its own. /sdd shows the exact Workflow({ ... }) call and waits for you to agree before launching it. You can also opt in yourself with a direct call or a plain-English request that names the workflow (see USAGE-EXAMPLES.md#running-workflows-directly). To watch running workflows, use /workflows. The cheaper options appear where they fit: /execute-task in chapter 06 and /simple-task in chapters 07 and 08.

Conventions used in every chapter

  • Bare skill names. Commands appear as /sdd, /write-spec, /execute-task, /deep-review, /simple-task. In plugin mode, type them with the plugin prefix: /sdd-kit:sdd, /sdd-kit:execute-task, and so on (INSTALLATION.md#namespacing).
  • No tracker. No Jira or Linear MCP server or CLI is connected. /sdd asks for the ticket text, Alex pastes it, and the step that posts a link back to the ticket is skipped.
  • Session location matters. Spec resolvers and single-file outputs (ADRs, review reports, execute-task state) are relative to the folder the session starts in. Each chapter says where to start Claude: the workspace root, or inside a repo with --add-dir for the other one (docs/multi-repo.md).
  • Simulated output is labelled, and abridged with ….
