08 — Proportionality: an S spec for the careers page (HIRE-7) and a no-spec trivial change (HIRE-8)

Chapters 04 to 07 ran M specs: schema changes, several layers, both repos. Most tickets are smaller than that, and the kit is built to scale down. This chapter takes two small tickets:

  • HIRE-7, a public careers page per company. It is a real feature with acceptance criteria, but it touches only web/ and needs no API change. write-spec sizes it S, so it gets the smallest spec there is: spec-lite.md plus tasks.md.
  • HIRE-8, salary ranges on job cards. It is one component and has no design choice, so /sdd routes it as trivial and /simple-task makes the change with no spec at all.

It assumes the state at the end of chapter 07: HIRE-3 to HIRE-6 are merged in both repos, and the demo data loads with php artisan migrate:fresh --seed.

Where to start Claude: the workspace root, ~/work/hireboard. Both tickets change only web/, but the session reads the API to confirm that nothing needs to change there.

Kit friction: where the spec folder lands. write-spec creates .ai/specs/<id>/ relative to the session's working directory and never asks where. From the workspace root that would be ~/work/hireboard/.ai/specs/, the untracked scratch folder. So Alex told the session up front that the spec belongs in web/ (chapter 05 does the same for api/), and the folder-creation step ran inside web/. The rule comes from docs/multi-repo.md: the spec lives in the repo that starts the change. The HIRE-3 to HIRE-6 specs live in api/ because the API starts them. This one lives in web/. If you would rather not rely on the instruction, start the session in web/ with CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../api instead, and pass the repos as { backend: "../api", frontend: "." }.

What an S spec contains

The whole spec is spec-lite.md and tasks.md. write-spec does not create decisions.md, and no Decisions section is written: the template marks it (when needed) and nothing here needed deciding. manual-test.md comes later from ship-feature's TestPlan phase, not from write-spec. Compare that with HIRE-4 in chapter 05, which needed decisions, business rules and seven tasks.

Step 3 — The code

The page is [app/companies/[slug]/page.tsx](artifacts/web/app/companies/%5Bslug%5D/page.tsx). It deliberately has no loading.tsx: a loading boundary starts streaming a 200 response before notFound() runs, so an unknown slug would never return 404. It is a Server Component that makes three calls through the existing fetchers in parallel:

export default async function CompanyPage({ params }: CompanyPageProps) {
  const { slug } = await params;

  if (!SLUG_PATTERN.test(slug)) {
    notFound();
  }

  const [company, jobs, reviews] = await Promise.all([
    getCompany(slug),
    searchJobs({ company: slug }),
    loadReviewSummary(slug),
  ]);

  if (!company) {
    notFound();
  }

  const averageRating = reviews?.meta.average_rating ?? null;
  const reviewCount = reviews?.meta.total ?? 0;
  // …

Four details, each tied to the spec:

  • params is a Promise (Next.js 15), so it is awaited before use.
  • SLUG_PATTERN guards the fetches. The pattern (/^[a-z0-9-]{1,80}$/) matches what the API accepts for the company filter. A slug outside it can never exist, and passing it to searchJobs({ company: slug }) would make the API answer 422 and land on the error boundary instead of the not-found page, so the page calls notFound() before any request.
  • loadReviewSummary catches only a 404. For an unknown slug the reviews endpoint answers 404 company_not_found at the same time as getCompany returns null. Without the catch, Promise.all would reject and AC-2 would show the error boundary. Any other error still surfaces.
  • The rating summary prints averageRating.toFixed(1) with "out of 5 · N reviews", or "No reviews yet" (clarity gate Q1). It always links to /companies/<slug>/reviews. The API already rounds half-up to one decimal (BR-43). The page only formats the number.

Alex asked for --no-tests on purpose. /simple-task is test-first by default (RED, then GREEN), and the flag is its explicit opt-out. The reason is that the web repo has no component test environment: Vitest covers lib/**/*.test.ts in a node environment, and the change is presentational. The cost is real. formatSalary has three branches of pure logic that nothing tests. Moving it to lib/format-salary.ts with a Vitest case would be the stricter alternative; chapter 10's QA plan lists the missing coverage.

The trivial signal in /sdd Step 2 is "≤ ~5 files, no design choice, no behavior contract at risk". This is the same line write-spec draws as XS: "≤ ~3 files, one obvious change … No spec. Recommend /simple-task". Had Alex routed it as a feature, write-spec would have sized it XS and sent it back to this route. /sdd never creates a spec for trivial work.
