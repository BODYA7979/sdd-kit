07 — Job applications with ship-feature, then /deep-review before merge (HIRE-6)

Previous: 06 — Build task by task and resume: candidate profiles with /execute-task

HIRE-6 is the first feature that moves personal data between two kinds of users. A candidate's name, email, headline and cover letter go to an employer, and only to the right one. The build follows the same feature pipeline as chapters 04 and 05: spec, human approval, then ship-feature. This chapter compresses those parts and spends its time on what happens after ship-feature reports SHIP. Alex Rivera gates the merge with /deep-review, a reviewer that never saw the spec or the prompt. It finds a real bug. Alex fixes it with a small /simple-task, re-reviews, and merges both repos in order.

What landed, by layer. Each file below is the complete end-of-walkthrough version.

API (api/):

  • Schema first: docs/schemas/job-applications.md, then the migration with UNIQUE (job_posting_id, candidate_id).
  • JobApplication model with a candidateProfile relation that joins on user_id = candidate_id, because User has no relations to later models. Also the factory.
  • SubmitApplicationDTO (only cover_letter comes from the body), and JobApplicationDTO with two outputs: toApiArray() for the candidate and toEmployerArray() for the employer.
  • JobApplicationRepositoryInterface / JobApplicationRepository, bound in RepositoryServiceProvider::$bindings.
  • JobApplicationService, JobApplicationPolicy, three exceptions (ProfileRequired, JobNotOpen, AlreadyApplied).
  • Three invokable controllers (Submit, ListMy, ListEmployer) and their own route file routes/api/v1/applications.php.
  • Tests: SubmitApplicationTest, ListMyApplicationsTest, ListEmployerApplicationsTest.

The core rule order is in the service:

$job = $this->jobPostings->findById($jobPostingId);

if ($job === null) {
    throw new JobPostingNotFoundException;
}

if (! $job->isOpen()) {
    throw new JobNotOpenException;
}

if (! $this->applications->hasCandidateProfile($candidateId)) {
    throw new ProfileRequiredException;
}

if ($this->applications->exists($jobPostingId, $candidateId)) {
    throw new AlreadyAppliedException;
}

return $this->applications->create($jobPostingId, $candidateId, $data->coverLetter);

findById() has no status filter on purpose. The apply flow has to find a closed posting so it can answer job_not_open rather than 404. That choice comes back in chapter 09, where the public detail endpoint turns out to share the unfiltered lookup.

Web (web/):

  • types/api/applications.ts mirrors both DTO outputs, and lib/api/applications.ts (server-only) holds the fetchers.
  • Three registry entries are added to web/lib/api/endpoints.ts (owned by chapter 02, which holds the final registry):
    submitApplication: { method: 'POST', path: '/api/v1/jobs/{id}/applications' },
listMyApplications: { method: 'GET', path: '/api/v1/me/applications' },
listEmployerApplications: { method: 'GET', path: '/api/v1/employer/applications' },
  • [/jobs/[id]/apply](artifacts/web/app/jobs/[id]/apply/page.tsx) with ApplyForm (useActionState) and submitApplicationAction. The action maps ApiError.code to messages and turns profile_required into a banner with a /profile link.
  • /applications and /employer/applications. Their middleware matchers and nav links already existed from HIRE-3.

What the adversarial depth does differently

No --depth means adversarial, the default:

  • A different agent and a different tier. The review is delegated to adversarial-reviewer. It runs on the deep tier, while ship-feature's Build phase wrote the code on the standard tier (docs/effort-guidelines.md). The reviewer is never the session that wrote the code.
  • No original prompt. It gets the code, docs/context/business-rules.md, docs/architecture.md and the gate results. It does not get the ticket, the spec's intent or ship-feature's report, so it judges what the code does, not what it was meant to do.
  • Skeptical persona with fixed criteria. It assumes every file has bugs until proven otherwise and applies 13 fixed review criteria. Each CRITICAL or MAJOR finding is re-read against the cited lines before it is reported.
  • security-auditor joins automatically because the scope touches authorization and personal data (candidate name, email, headline, cover letter). It runs in parallel and its findings are merged into the same report.

Why F1 is real

The service checks exists() and then inserts. A double click on Send application, or two open tabs, sends two requests that can both pass exists() before either inserts. The unique index stops the second row, which keeps the data correct, but the UniqueConstraintViolationException is not a BusinessRuleException. It reaches the global handler as a generic 500, and the form shows an error for an application that was in fact stored.

The AC-4 test (refuses a duplicate application) seeds the first application with a factory before posting, so it only ever exercises the pre-check. The spec said "even under a race", the test proved something narrower, and the build's Converge and Review phases both read "AC-4 has a test" as covered. The adversarial reviewer didn't know what AC-4 was meant to prove. It read the code, saw two statements that are not atomic, and asked what happens between them.

The new test calls the repository twice. That skips the service's exists() check, which is exactly the state two racing requests are in:

it('maps a concurrent duplicate insert to already_applied', function () {
    $candidate = applicantWithProfile();
    $job = JobPosting::factory()->open()->create();
    $repository = app(JobApplicationRepositoryInterface::class);

    $repository->create($job->id, $candidate->id, null);

    expect(fn () => $repository->create($job->id, $candidate->id, 'Second click.'))
        ->toThrow(AlreadyAppliedException::class);

    assertDatabaseCount('job_applications', 1);
});

F2 is not only a security note. AC-7, which Maya approved, says the employer list is paginated with per_page 1-50 (BR-11), and the controller passed per_page through unclamped. The build therefore missed an approved criterion, and both Converge ("every AC has a test") and the Review panel called AC-7 covered because a test existed for its other clauses. The SDD loop checks that each criterion has a test, not that the test asserts every clause. The adversarial pass caught it.

/deep-review complements ship-feature's Review phase. It does not replace it. ship-feature's panel reviews the build with the spec: four dimensions, and each finding has to survive a three-vote refutation. That makes it good at "does this match what we agreed?". /deep-review at the adversarial depth deliberately works without the spec or the prompt, so it catches what everyone who read the spec agreed not to look at. Here, everyone who read "even under a race" assumed the AC-4 test proved it. Use both for anything that touches auth, personal data or money. For the scenario-level summary, see USAGE-EXAMPLES.md#9-review-before-merge.
