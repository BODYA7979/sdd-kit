Step 3: What each phase does

The phases below are the meta.phases of greenfield-build.js. The log lines use the workflow's own log() formats. All output is simulated and abridged.

Detect

A code-explorer agent probes both targets. Its prompt asks for git -C <path> ls-files, but the shipped code-explorer agent is read-only (Read, Grep, Glob), so it cannot run git unless your setup grants it Bash. Here both directories are missing, so there is nothing to find either way (Glob matches no files), and the target counts as greenfield.

Detect: backend:laravel@api, frontend:nextjs@web (split); greenfield=true

If api/ or web/ already contained source files, the run would stop here with BLOCKED. That is why chapter 01 never creates them (friction F1). Treat the git-tracked check as best effort: with the read-only agent the file-presence check is what actually protects you.

Constitution

A deep-tier agent turns the conventions into testable principles before any architecture is decided. It reads the workspace CLAUDE.md, which loads the invariants INV-01..INV-07 and points to product-brief.md. It also consults the kit skills for the detected stacks.

Constitution: 9 principle(s), skills: laravel-12, service-repository, dto-first, api-design, schema-first, nextjs-15, typescript, tailwind-4, architecture-patterns

Principles it returned (abridged): "controllers are single-action and invokable; logic lives in services", "DTOs at every layer boundary, repositories return DTOs", "schema documented in docs/schemas/ before the migration", "one envelope for success and error (INV-01)", "the browser never calls the API (INV-05)", "every browser-facing endpoint is in one registry (INV-06)".

Architecture, with a 3-vote verify

One deep agent proposes the architecture, then three standard agents try to refute it through three lenses: principle-adherence, simplicity and stack-fit. A majority of "holds up" votes marks it sound.

Architecture: slice "Visitor searches open jobs and opens one" — sound (2/3)

What it decided, and what ended up in api/docs/architecture.md:

  • Layout: split, api/ and web/.
  • Layers: route → invokable controller → service (DTOs) → repository interface → Eloquent, and app router page (Server Component) → lib/api → API.
  • Data model sketch: companies (uuid, slug, owner_id nullable) and job_postings (uuid, status, published_at, salary_* integers).
  • First slice: entry point /jobs, expected end state "the visitor filters by Remote, opens a card and sees the job with its company".
  • Decisions: domain tables use UUIDs while users keeps bigint ids, so Sanctum works unchanged (A3); auth is deferred to a separate decision, which becomes ADR-0001 in chapter 03 (A10).

The simplicity voter refuted it, with the reason that repository interfaces are more than one slice needs. Two of three still voted "holds up", so the architecture stands and keeps the interfaces because INV-02 requires them. The workflow passes the reasons of refuting votes to the final report as concerns, so read them there.

Gates

Gates run per repo, in parallel. A failing gate triggers a fix round (at most three), and the fixer is told to fix the code, not suppress the error.

Gates round 1: fixing 1 failing gate(s)

Round 1 in this run: PHPStan reported that JobPostingDTO::fromModel() passed a string where EmploymentType, JobPostingStatus and CarbonInterface were expected. Larastan had resolved those attributes from the migration column types for these two models. The fixer didn't loosen the DTO types. It added @property docblocks to Company and JobPosting that state the cast types, and the second gate run was green in both repos. Whether a model needs such docblocks depends on the model and the Larastan version, so add them only where PHPStan reports the mismatch.

Acceptance

A deep agent ignores the passing unit tests and walks the real journey. It boots php artisan serve --port=8000 and npm run dev, then drives http://localhost:3000:

Step 4: Read the slice code

The finished code is in the artifacts. These excerpts show how a request moves through it.

API: one request, four layers

routes/api.php contains no routes. It prefixes v1 and loads one file per feature, so later feature branches each add their own file and never touch a shared one (artifacts/api/routes/api.php):

Route::prefix('v1')->group(function (): void {
    foreach (glob(__DIR__.'/api/v1/*.php') ?: [] as $routeFile) {
        require $routeFile;
    }
});

routes/api/v1/jobs.php maps the three public endpoints to invokable controllers. The search controller builds the input DTO and calls one service method. $request->boolean() handles remote=0, which would otherwise be a truthy string (GOTCHA-03 in api/CLAUDE.md):

// app/Http/Controllers/Jobs/SearchJobPostingsController.php
public function __invoke(Request $request): JsonResponse
{
    $filters = JobSearchDTO::validateAndCreate([
        ...$request->only(['q', 'location', 'employment_type', 'company', 'page', 'per_page']),
        'remote' => $request->filled('remote') ? $request->boolean('remote') : null,
    ]);

    return $this->paginated($this->jobs->search($filters));
}

JobSearchDTO maps snake_case input to camelCase properties with #[MapInputName(SnakeCaseMapper::class)]. It also validates: an unknown employment_type or per_page=0 produces a ValidationException, which bootstrap/app.php renders as 422 validation_failed. JobPostingService::search() caps per_page at 50 (BR-11) and calls the repository through its interface. JobPostingRepository::searchOpen() is the only place that knows about Eloquent. It filters on status = open (BR-10), sorts newest first, and maps every row to a JobPostingDTO. The binding lives in RepositoryServiceProvider::$bindings, registered in bootstrap/providers.php.

Responses go out through JsonResponseTrait, which the base Controller uses. paginated() serializes each DTO with toApiArray() and adds the INV-01 meta:

{ "success": true, "status": 200, "message": "OK", "data": [ { "id": "9d3c…", "title": "Senior Laravel Engineer", "…": "…" } ],
  "meta": { "current_page": 1, "per_page": 20, "total": 8, "last_page": 1 } }

Errors take the other path. A service throws a BusinessRuleException subclass, such as JobPostingNotFoundException (404, job_not_found). bootstrap/app.php renders it, and also validation, 401, 403, 404 and 429 errors, in one error envelope for everything under api/*. No controller catches anything.

The tests pin the behavior: SearchJobPostingsTest ('lists only open postings newest first', 'filters by keyword, location, remote, employment type and company', 'caps per_page at 50', 'returns the pagination meta'), ShowJobPostingTest and ShowCompanyTest. tests/Pest.php applies RefreshDatabase to every feature test.

Web: a Server Component, a parser, one client

app/jobs/page.tsx awaits the Next 15 searchParams promise, parses it, and fetches on the server. Reading searchParams makes the page dynamic, so npm run build never calls the API:

export default async function JobsPage({ searchParams }: JobsPageProps) {
  const filters = parseJobFilters(await searchParams);
  const { data: jobs, meta } = await searchJobs(filters);
  // ...JobFilters, a list of JobCard, Previous/Next links built with toQueryString()
}

lib/search-params.ts drops empty and unknown values, so a hand-edited URL never turns into an API 422. It is the one piece of pure logic, and the Vitest test covers it (lib/search-params.test.ts).

lib/api/jobs.ts calls apiFetch('searchJobs', { query }). lib/api/client.ts starts with import 'server-only', looks the endpoint up in the registry, and builds the URL from the server-only API_BASE_URL. It always fetches with cache: 'no-store', so a posting that closes disappears on the next request, and it throws ApiError { status, code, errors } on any non-2xx response. getJob() turns a 404 into null, and app/jobs/[id]/page.tsx turns null into notFound().

// lib/api/endpoints.ts: the INV-06 registry (excerpt)
export const endpoints = {
  searchJobs: { method: 'GET', path: '/api/v1/jobs' },
  showJob: { method: 'GET', path: '/api/v1/jobs/{id}' },
  showCompany: { method: 'GET', path: '/api/v1/companies/{slug}' },
  // ...
} as const satisfies Record<string, EndpointDefinition>;

JobFilters is a GET form (next/form), not a client component with state. Submitting it navigates to /jobs?…, so every search is a shareable URL. JobCard renders one posting. types/api/jobs.ts mirrors the API shape field for field, with enum literal unions copied from App\Enums.
