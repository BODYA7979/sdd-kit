Major Issues (should fix)

[MAJOR] F1: Check-then-insert race returns 500 instead of 409 already_applied

File: app/Repositories/JobApplicationRepository.php:31 Category: data-integrity

Issue: JobApplicationService::submit() (app/Services/JobApplicationService.php:50) calls exists() and then create(). Two concurrent submits for the same candidate and posting (a double click, or two tabs) can both pass exists(). The second INSERT then violates job_applications_job_posting_id_candidate_id_unique, and the resulting Illuminate\Database\UniqueConstraintViolationException is not a BusinessRuleException, so the handler in bootstrap/app.php renders it as a generic 500. BR-32 says "409 already_applied, also under a concurrent duplicate insert", so the second request must get a 409. The unique index keeps the data correct; the response is what is wrong. The web form then shows a generic error for an application that actually exists.

Current Code:

public function create(string $jobPostingId, int $candidateId, ?string $coverLetter): JobApplicationDTO
{
    $application = JobApplication::query()->create([
        'job_posting_id' => $jobPostingId,
        'candidate_id' => $candidateId,
        'cover_letter' => $coverLetter,
    ]);

    return JobApplicationDTO::fromModel($application->load(self::RELATIONS));
}

Recommended Fix:

try {
    $application = JobApplication::query()->create([...]);
} catch (UniqueConstraintViolationException) {
    throw new AlreadyAppliedException;
}

Add a test that calls the repository's create() twice for the same pair. That bypasses the service pre-check, which is exactly the race.

Impact: a user-facing 500 under a common interaction (double submit), and a misleading error message for an application that was stored.

Positive Observations

  • The employer list is scoped in SQL (whereHas('jobPosting.company', owner_id)) rather than filtered after fetching, so another company's applications never reach PHP memory.
  • JobApplicationDTO::toEmployerArray() is an explicit allow-list (name, email, headline). Adding a profile column cannot leak through it by accident (BR-21).
  • Rule order in submit() (found, open, profile, duplicate) avoids asking for a profile for a job that cannot be applied to.
  • findById() versus a status-filtered lookup is documented at the call site, which protects the job_not_open behavior from a well-meant "fix".
  • The browser never sees the token: the apply form posts to a Server Action, and lib/api/applications.ts is server-only (INV-05).
