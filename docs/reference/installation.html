Installing SDD Kit

How to install, update, upgrade, and remove the kit in either mode, plus what the installer changes and how to set up MCP servers. For your first session after installing, see GETTING-STARTED.

Install jq with brew install jq or apt-get install jq.

New to Claude Code? Install it first: GETTING-STARTED, section 0.

Choose a mode

  • Plugin mode: install from the marketplace; one pinned version per team, updated with /plugin.
  • File-copy mode: ./install.sh merges the kit into .claude/; you can edit agents and skills in place.
  • Both ship the same agents, skills, workflows, and hooks. The full comparison (hooks, permissions, namespacing, limitations) is in plugin-mode.md.

Plugin mode

Install

/plugin marketplace add stasmarkov/sdd-kit
/plugin install sdd-kit-laravel-nextjs@sdd-kit   # preset: core + Laravel + Next.js + devenv

The core plugin is stack-neutral. Stack knowledge lives in add-on plugins; the preset sdd-kit-laravel-nextjs installs the core and the Laravel, Next.js and devenv add-ons in one step (Claude Code resolves its dependencies). To pick pieces yourself, install the core and the add-ons you need:

/plugin install sdd-kit@sdd-kit
/plugin install sdd-kit-laravel@sdd-kit  # Laravel agent, skills, rules, hooks
/plugin install sdd-kit-nextjs@sdd-kit   # Next.js agent, skills, rules, hooks
/plugin install sdd-kit-devenv@sdd-kit   # docker and ddev skills
/plugin install sdd-kit-ops@sdd-kit      # deploy, rollback, feature flags, health checks, incidents
/plugin install sdd-kit-ios@sdd-kit      # iOS/Swift agent and skills
/plugin install sdd-kit-drupal@sdd-kit   # Drupal 11 skill
/plugin install sdd-kit-design@sdd-kit   # UI/UX agent and /design-ui

To work from a local checkout (developing the kit, or testing an unreleased branch), skip the marketplace and load the directory directly. Pass --plugin-dir once per plugin:

claude --plugin-dir /path/to/sdd-kit/plugins/sdd-kit \
       --plugin-dir /path/to/sdd-kit/plugins/sdd-kit-ops

Namespacing

This guide uses bare skill names (/sdd, /write-spec), which is what file-copy mode gives you. Plugin mode prefixes every skill with its plugin name: /sdd-kit:sdd, /sdd-kit:framework-doctor, /sdd-kit-ops:deploy.

Project context is not installed

Plugins do not create CLAUDE.md, AGENTS.md, or .claude/rules/. Copy them from the repo by hand:

cp /path/to/sdd-kit/share/CLAUDE.template.md CLAUDE.md
cp /path/to/sdd-kit/share/templates/AGENTS.template.md AGENTS.md
mkdir -p .claude/rules && cp /path/to/sdd-kit/share/templates/rules/*.md .claude/rules/

How to fill them in is covered in GETTING-STARTED.

Update and uninstall

/plugin marketplace update sdd-kit   # refresh the catalog
/plugin update                       # update installed plugins
/plugin uninstall sdd-kit@sdd-kit    # repeat for each add-on
/plugin marketplace remove sdd-kit

Team rollout

To pin a reviewed version for a whole team, publish your own marketplace that points at a release tag and commit. See team-marketplace.md.

File-copy mode

git clone https://github.com/stasmarkov/sdd-kit.git
cd /path/to/your-project
/path/to/sdd-kit/install.sh --project --dry-run   # preview
/path/to/sdd-kit/install.sh --project             # install

Run the installer from your project root: --project installs into ./.claude of the current directory. With no flags it asks where to install, defaults to a full install, shows the change list, and asks before writing anything.

Without cloning: npx

From your project root, npx github:stasmarkov/sdd-kit install --project --dry-run previews and npx github:stasmarkov/sdd-kit install --project installs; every install.sh flag below works (--minimal, --full, --with=ops, --yes, --user). It runs the same install.sh as a clone, so the result is identical, and it needs bash, git, jq and Node 18+. On Windows use Git Bash or WSL, or the plugin.

Add #v2.1.0 to pin a release (npx github:stasmarkov/sdd-kit#v2.1.0 install --project); without a tag npx fetches the default branch. npx caches the download. The package is not published to npm.

Examples:

./install.sh --project --minimal
./install.sh --project --with=ops,design
./install.sh --user --full --yes

Stacks and add-ons: two axes

--stack picks the stack add-ons and --with picks the optional ones. They are independent.

  • Fresh install, no --stack: laravel,nextjs are installed. devenv is added to the defaults even when --with names other add-ons, so --with=ops installs laravel, nextjs, devenv and ops.
  • --with given: the optional add-ons are exactly the list you pass (plus the devenv rule above when --stack is absent).
  • --stack=none with a stack add-on in --with is an error.
  • Upgrade: flags and prompt answers add to what is installed. Add-ons you do not mention are kept (Keeping installed add-on in the plan).
  • --prune: makes the installed set exactly your selection: stacks exactly --stack, non-stack add-ons exactly --with (the installed non-stack set when --with is omitted). Removed files are backed up, and files you modified are kept and listed (Removing add-on '<x>' (--prune) in the plan).

Add-on templates (for example the Laravel contract-sync template) are staged to .claude/templates/<addon>/. Add-on rules and add-on third-party.json fragments are file-copy only: plugin mode has no rules directory and ships no third-party fragments, so copy them from the add-on if you need them. Rules are copied into .claude/rules/ only when absent, in project mode.

Non-interactive behaviour: prompts read the terminal device, never stdin. With --yes, or when no terminal is available, nothing is asked and the defaults above apply (pass --project or --user too). There is no piped install; clone the repository (or use npx) and run install.sh as a command.

Building from source

Contributors build the distribution tree and plugin archives from the source repository with ./build.sh. It runs ./verify.sh first, then writes one plugin archive per plugin to dist/. dist/ is gitignored: release artifacts are published to stasmarkov/sdd-kit by CI. There is no single-file installer; use the install.sh in a clone of stasmarkov/sdd-kit, or the npx form above.

What the installer does

  1. Merges, never replaces. Files the kit does not own are never touched. Your own skills, agents, and settings stay as they are.
  2. Reports first. It prints added / updated / removed counts and the paths before writing.
  3. Records a manifest. .claude/.framework-manifest lists every installed file with its hash; .claude/.framework-version holds the version. The next run uses the manifest to update changed files and remove files the kit no longer ships.
  4. Removes retired files. Files that 1.x installed but 2.0 dropped (merged agents, knowledge-graph scripts) are removed even when no manifest exists yet.
  5. Keeps the latest backup. Every file it overwrites or removes is copied to .claude/.framework-backups/<timestamp>/. Older framework backups are pruned.
  6. Merges hooks into settings.json via src/scripts/install-hooks.sh (needs jq). A missing file is created; an existing one is backed up to settings.json.backup.<timestamp> and only the kit's own hook entries are replaced. Permissions, env, model, and your own hooks are preserved. Invalid JSON is left untouched and reported.
  7. Merges context7 and playwright into .mcp.json (project mode). Existing servers win on name conflicts. In user mode it prints the commands instead: claude mcp add --scope user context7 -- npx -y @upstash/context7-mcp and claude mcp add --scope user playwright -- npx -y @playwright/mcp@0.0.83 --headless --isolated.
  8. Creates project context when absent (project mode only): CLAUDE.md from src/CLAUDE.template.md, AGENTS.md from src/templates/AGENTS.template.md, and .claude/rules/ from src/templates/rules/. Existing files are never overwritten.
  9. Sets the spec-aware status line (scripts/statusline.sh: active spec, task, model) only if settings.json has no statusLine yet.

Re-running the installer is the update path. Use --dry-run to see the diff first.

MCP servers

The kit enables two servers by default:

  • context7: current library and framework docs.
  • playwright: Playwright MCP, pinned to one version and started with --headless --isolated (no visible window, no profile kept between runs). Remove --headless from its entry to watch the browser.

Everything else is opt-in. Optional servers are defined in src/mcp-configs/development.json, installed as .claude/mcp-configs/development.json. To enable one, copy its block into your project .mcp.json under mcpServers, or add it with claude mcp add.

Examples with the CLI:

claude mcp add --transport sse phpstorm http://localhost:64342/sse

  --header "Authorization: Bearer $GITHUB_TOKEN"

Keep secrets in environment variables (${GITHUB_TOKEN}), never inline in .mcp.json, which is usually committed.

Browser checks. Every workflow's Reproduce, Visual, and Acceptance steps drive the browser with Playwright MCP: they assert on the page's accessibility snapshot and check console errors and failed network requests on every page. When the Playwright tools are unavailable they fall back to Claude in Chrome, and when neither is available they report the check as "not run", never as passed. For web stacks Playwright is also a quality gate, and ship-feature turns the acceptance walk into an e2e/<spec>.spec.ts test traced to the acceptance criteria.

Recommended settings

These are environment choices the installer leaves to you.

Code intelligence (LSP). The php-lsp and typescript-lsp plugins give Claude post-edit diagnostics (type errors, missing imports) and precise navigation instead of grep-only search. They are listed in src/settings/third-party.json; --third-party prints the install commands, or run them yourself:

/plugin install php-lsp@claude-plugins-official
/plugin install typescript-lsp@claude-plugins-official

See third-party.md for the review policy behind the list.

Permissions and sandboxing. Permission mode and sandboxing depend on your machine and threat model, so the kit does not force either, and the installer does not write any permissions into your settings.json. The repo's root settings.json carries a conservative permissions.allow / permissions.deny list (read-only git, test and lint runners; denies rm -rf, force-push, git reset --hard) and env.CLAUDE_BUDGET_THRESHOLD. Copy what you want from it into your own settings.json, in either mode. A plugin's settings.json does not apply these keys; see plugin-mode.md. To opt in to a stricter defaultMode or sandbox, set them in your own settings.json. Filesystem sandboxing limits where Claude can write; do not rely on network sandboxing as a security control.

Read rules for overlay stacks. Workflows read four locations outside the project: the trust store, the user stacks directory, the installed plugin list and the plugin cache that holds each installed plugin's stack.json. Claude Code asks before such a read and a workflow agent cannot answer, so until they are allowed every overlay stack manifest (a project or user stacks/*.json, or a third-party plugin's stack.json) is treated as untrusted and its gates are not run. The kit's own stacks are not affected. /stack-trust offers to add exactly these rules to your user settings, and /framework-doctor warns when one is missing:

Read(~/.claude/sdd-kit/trusted-stacks.json)
Read(~/.claude/stacks/**)
Read(~/.claude/plugins/installed_plugins.json)
Read(~/.claude/plugins/cache/**)

With CLAUDE_CONFIG_DIR set, the last three name that directory as an absolute path instead; run /stack-trust to get the exact text. The trust store itself always lives in ~/.claude/sdd-kit/trusted-stacks.json in your home directory as the operating system's user database records it: neither $HOME nor CLAUDE_CONFIG_DIR moves it.

Model tiers and effort per workflow phase are covered in effort-guidelines.md.

Upgrading from 2.x

3.0 moves the Laravel, Next.js and docker/ddev components out of the core into add-ons.

Plugin mode. Install the preset, /plugin install sdd-kit-laravel-nextjs@sdd-kit, to keep what 2.x gave you. Namespaces follow the plugin that ships the component: /sdd-kit-laravel:laravel-12, agents sdd-kit-laravel:laravel-backend-dev and sdd-kit-nextjs:nextjs-frontend-dev. Claude Code installs the preset's dependencies; on claude.ai install each add-on yourself. A SessionStart hint suggests the matching add-on once per project.

File-copy mode. Re-run install.sh (use --dry-run first). With no --stack it installs the Laravel and Next.js add-ons, plus devenv on a fresh install. Moved files are replaced at their new paths, old paths are retired, and every overwritten or removed file is backed up to .claude/.framework-backups/<timestamp>/. A user agent with the same name as an add-on agent wins: the staged copy is dropped and the installer prints the fix. Use --prune to drop add-ons you no longer want. Bare names keep working (/laravel-12, /migrate-db, agent laravel-backend-dev).

Upgrading from 1.x

Re-run the 2.0 installer (or update the plugin). In file-copy mode it removes the files 1.x installed that 2.0 no longer ships (retired agents, skills, templates, and scripts) and backs them up first. It only removes a file whose content matches a copy the kit shipped; a file you edited or replaced (for example an upstream Stripe or skill-creator skill installed at the same path) is listed as "kept (modified or not from the kit)" and left for you to review.

The tables below match the CHANGELOG's Migrating from 1.x section. They list what a 1.x release shipped; components that were added and removed again during the 2.0 cycle appear only in the CHANGELOG's Removed table. Current lists: skills, agents.

Knowledge graph retired

Memory is now Claude Code auto memory plus agent memory (memory: project in agent frontmatter). The installer already removes the knowledge-graph-manager and learning-extractor agents, scripts/kg-capture.sh, scripts/init-knowledge-graph.js, and hooks/post-change-kg-sync.sh, and drops the kg-capture hook from settings.json. It does not touch your data or MCP config, so finish the cleanup by hand:

  1. Remove the knowledge-graph entry from mcpServers in .mcp.json (or claude mcp remove knowledge-graph).
  2. Delete .claude/knowledge-graph.jsonl and .ai/knowledge-graph.jsonl if present. Move anything worth keeping into CLAUDE.md, AGENTS.md, or .claude/rules/ first.

Other leftovers

  • 1.x left *.backup.* copies inside .claude/. The installer warns about them; delete them once you no longer need them.
  • Cards in a 1.x .ai/kanban.json are not read by /spec-board, which takes status from the spec files. A card with a spec needs nothing. Drop the DONE, IN_PROGRESS, and REVIEW cards that have no spec: that work is already started or finished, and a backlog slice would re-plan it. Migrate only the BACKLOG and TODO cards without a spec: paste their titles and descriptions into /product-brief --intake "<cards>" (with no product-brief.md yet, it offers to write the brief first or to start a backlog only), or turn one into a spec with /write-spec. Then delete the file.
  • Documents imported with 1.x /workflow:add-context into .claude/context/business/, .claude/context/architecture/, or .claude/context/workflow/ are no longer read by anything: their only readers were the retired context-fetcher agent and the knowledge graph. Re-import each one into the Golden Triangle paths that /write-spec, create-spec, and /framework-doctor read: /write-docs --import .claude/context/<dir>/<file> --as=business (or --as=architecture, --as=api; for workflow/ files, pick the one that fits or fold them into AGENTS.md). Then delete .claude/context/. /framework-doctor warns while it exists.
  • docs/context/workflow.md from 1.x /workflow:getting-started is no longer generated, and CLAUDE.md no longer loads it. The SessionStart (compact) hook still re-injects its first lines after a compaction while the file exists, so fold anything still true into AGENTS.md (commands, red lines) and delete it.
  • Files the installer kept because they no longer match the kit's copy are listed as "kept" in its plan; review each and delete the ones you do not use (a kept 1.x agent in a category folder, such as agents/quality/code-reviewer.md, still loads next to the flat 2.0 agents).
  • A 2.0 --minimal install ships no .claude/commands/, so a 1.x full install's namespaced commands stay behind. /framework-doctor flags them; delete the namespaced folders (upstream/, quality/, execution/, workflow/, _shared/, and so on) under .claude/commands/.

Uninstalling

Plugin mode: /plugin uninstall sdd-kit@sdd-kit and the same for each add-on.

File-copy mode: there is no --uninstall flag. The manifest lists every file the kit installed (second column), relative to .claude/:

cd .claude
awk '{print $2}' .framework-manifest | xargs rm -f
find agents skills commands templates hooks docs workflows settings mcp-configs \
     output-styles scripts -type d -empty -delete 2>/dev/null
rm -f .framework-manifest .framework-version

Then remove the kit's hook entries and statusLine from settings.json (or restore the settings.json.backup.<timestamp> taken at install), and the context7 and playwright entries from .mcp.json if you don't want them. CLAUDE.md, AGENTS.md, and .claude/rules/ are yours after creation; keep or delete them. Files the installer overwrote or removed on its last run are in .claude/.framework-backups/<timestamp>/ if you need to restore them.

Troubleshooting

Hooks don't fire. Check jq --version: both the installer and the hook scripts need it. If the installer printed "Hooks were NOT installed", settings.json was probably invalid JSON; fix it and re-run. Then run /hooks and /framework-doctor. In plugin mode hooks come from the plugin's hooks/hooks.json, not your settings.json.

An MCP server doesn't start. context7 and other npx servers need Node.js on the PATH Claude Code sees. Run claude mcp list to see status, and check the server's requirement in the MCP table (uv for Serena, the Composer package for laravel-boost, the env var for GitHub/Obsidian). In user mode .mcp.json is not written; run the claude mcp add command the installer printed.

Browser checks say "not run". The Playwright MCP server did not start or its tools were not available to the workflow.
