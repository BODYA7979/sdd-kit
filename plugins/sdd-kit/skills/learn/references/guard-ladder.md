# Guard ladder: patterns per rung

Load this when drafting the guard in `/learn` Step 3. Each rung says where the guard goes and what makes it a bad fit. Stack examples (architecture tests, analyzer and linter configuration) live in the stack add-on's conventions skill under `references/guard-ladder.md`; match the target project's existing files and style over any example.

## Rung 1: regression or architecture test

Append to the project's existing architecture test file (grep for it under the test directory), or add one beside the other tests of that area. Name the test after the rule, not the incident (`controllers do not query`, not `fix export bug`). A rule can be an architecture expectation (forbidden dependency, naming, layering) or a behavior test over several inputs (a dataset or table) rather than one fixed case. When known violations exist, an `ignoring` list keeps the guard green while they are fixed; list each ignored path in the diff so the user approves it explicitly.

**Bad fit for rung 1:** the rule needs judgment ("names should be clear"), or a test would have to parse source text with regexes. Move down the list to rung 2 or 3.

## Rung 2: static analysis rule

Only configure tools the project already runs in its gates. Never add a dependency to enable a guard. Options in order of cost: raise the analysis level for a path that keeps producing the class; turn on a parameter an installed extension already offers; a restricted-import or restricted-syntax lint rule with a message that says what to do instead; a custom rule class only when a test cannot express the class. Scope the rule to the files where the class applies. Never use an ignore list or the baseline to make a new guard green.

**Bad fit for rung 2:** the analyzer cannot see the pattern without a new plugin, or the rule would flag legitimate code in more places than it catches mistakes.

## Rung 3: path-scoped rules line

Pick the `.claude/rules/<file>.md` whose `paths:` globs cover the evidence file (the core `tests.md` and the rules the stack add-ons install). Add one imperative bullet to the section it belongs to, with the reason in the same line.

```diff
 ## Talking to the backend

 - All backend calls go through the typed API client. No ad-hoc requests in components.
+- Server-side handlers re-validate input with the same schema as the API; never trust the client-side check.
```

- If no rules file covers the path, use rung 4. Propose a new rules file only when there are already two or more lessons for the same paths.
- If the new line contradicts an existing one, show both and ask which wins; never leave both.

**Bad fit for rung 3:** the rule applies across the whole codebase (rung 4), or a tool could enforce it (rungs 1-2).

## Rung 4: CLAUDE.md INV or GOTCHA entry

Choose the type:

| Entry | Use for | Shape |
|-------|---------|-------|
| `INV-NN` | A rule that must hold everywhere; specs and reviews cite it | `- **INV-NN** <Rule>. <Consequence of breaking it.>` |
| `GOTCHA-NN` | A confirmed trap that looks right but is not | `- **GOTCHA-NN** <Symptom>, because <cause>. <Correct approach>. (seen: <file:line or ticket>)` |

```diff
 ## Gotchas
 ...
 - **GOTCHA-03** Frontend enum literals type-check but must match backend values exactly.
+- **GOTCHA-04** Queued listeners see stale data, because the job serializes the record before the transaction commits. Dispatch after commit. (seen: app/Listeners/SendRefundEmail:22)
```

- Number = highest existing number + 1, two digits. Never reuse a number, even from a removed entry.
- Keep fixed entries and annotate them (`FIXED by spec-0051`, `guarded by tests/Unit/ArchTest`), as the CLAUDE.md template asks.
- If the section does not exist, add it with the template heading (`## Invariants` / `## Gotchas`) and its one-line intro, after `## Task routing` when present.
- One or two lines per entry. CLAUDE.md is loaded every session; a long entry is a recurring cost.

**Bad fit for rung 4:** the lesson is specific to a few files (rung 3) or enforceable by a tool (rungs 1-2).

## Rung 5: hook (proposal only)

Hooks change what Claude Code executes, so they need the owner's approval and are never written by `/learn`. Use this rung only when the mistake is an action no test or rule sees in time: editing a generated file, running a destructive command, ending a session without a required step.

Print the proposal in this shape:

```
Hook proposal (not applied: needs the owner's approval)
Event:     PreToolUse
Matcher:   Edit|Write
Check:     block edits to generated files (regenerated by tooling)
Behavior:  exit 2 with "Generated file: run the generator instead" (blocks the call, reason goes to Claude)
Goes in:   the project's .claude/settings.json "hooks" (both modes; the kit's own hooks/hooks.json is never edited for a project rule)
Script:    .claude/scripts/block-generated.sh, sketched below
Why not rungs 1-4: the mistake happens at edit time; a test only fails after the damage
```
